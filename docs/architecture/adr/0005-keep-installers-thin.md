# install 스크립트는 패키지 설치와 설정 배포만 한다

## 맥락과 문제

#10 이전의 install은 설치한 것을 설치 기록(receipt)으로 추적하고, 파일마다 소유권 모드를 판정했다. 도구 버전을 고정하고 SHA-256으로 검증했으며, uninstall 스크립트, PATH 정리, 설치 후 검증 스크립트, 계약 테스트와 이를 확인하는 CI 잡을 두었다. PR #10 본문에 따르면 저장소는 약 14,000줄이었다. install이 어디까지 책임질 것인가?

## 판단 기준

- 모든 OS에서 같은 단계를 유지할 수 있을 만큼 코드가 작아야 한다
- 여러 번 실행해도 안전해야 한다

## 검토한 선택지

- 패키지 매니저와 공식 installer를 부르고 설정 파일만 배포한다
- 설치 기록, 소유권 판정, 버전 고정, uninstall을 유지한다

## 결정

"패키지 매니저와 공식 installer를 부르고 설정 파일만 배포한다"를 선택한다. #10에서 설치 기록, 소유권 판정, 고정 버전과 SHA-256 검증, uninstall, 검증 스크립트, 계약 테스트를 걷어냈다. PR #10 본문에 따르면 저장소는 약 1,700줄이 됐다.

### 결과

- 장점: 코드가 크게 줄었고, OS별 install 스크립트의 단계가 같은 순서로 맞춰졌다
- 단점: uninstall이 없다. 지울 때는 패키지 매니저와 각 도구의 방법을 쓴다
- 단점: 매니페스트에서 뺀 도구가 기존 머신에 남는다. #10 이전 설치본은 [구버전 설치 잔재 정리](../../legacy-cleanup.md)로 정리한다
- 단점: 버전을 고정하지 않아 업스트림의 변경이나 오염이 다음 install에 그대로 들어온다. [외부 코드](../../../SECURITY.md#외부-코드)의 확인 항목으로 보완한다
- 단점: 덮어쓰기 대상은 백업하지 않는다. 원본은 git에 있고, 사용자가 고칠 수 있는 파일은 병합이나 마커 블록으로 배포한다

### 확인 방법

- #10에서 Windows는 가짜 홈에서 `install.ps1`을 두 번 실행했고, Linux는 새 Ubuntu 24.04(WSL)에서 `install.sh`를 여러 번 실행해 두 번째부터 결과가 바뀌지 않음을 확인했다. macOS는 실행하지 않았다.
- 이 범위를 넘는 기능은 [범위](../../standards/installer.md#범위)에 따라 ADR로 먼저 제안한다.
