# 앱이 다시 쓰는 설정 파일은 기존 값이 이기도록 병합한다

## 맥락과 문제

에이전트와 터미널 도구의 설정 파일 중에는 앱이 실행 중에 스스로 고쳐 쓰는 것이 있다(Claude Code의 `settings.json` 등). Orca 같은 다른 도구도 `settings.json`에 hook을 넣는다. 이 파일을 덮어쓰면 그 값이 사라지고, 배포하지 않으면 새 머신에 저장소 설정이 들어가지 않는다. 이런 파일을 어떻게 배포할 것인가?

## 판단 기준

- 사용자와 다른 도구가 넣은 값을 지우지 않아야 한다
- 저장소에 새로 추가한 키는 기존 머신에도 들어가야 한다
- 백업 없이 여러 번 실행해도 안전해야 한다

## 검토한 선택지

- 기존 값이 이기는 병합
- 저장소 값이 이기는 병합
- 덮어쓰기
- 파일이 없을 때만 복사

## 결정

"기존 값이 이기는 병합"을 선택한다. 판단 기준을 모두 충족하는 선택지는 이것뿐이다. install 스크립트의 병합 헬퍼가 jq와 yq로 저장소 파일 위에 기존 파일을 겹친다. 병합 대상 파일은 install 스크립트의 `config files` 단계가 정한다.

### 결과

- 장점: 사용자가 바꾼 값, 한글 값, 다른 도구의 hook이 보존된다
- 장점: 저장소에 새로 추가한 키는 기존 머신에도 들어간다
- 단점: 저장소에서 기존 키의 값을 바꾸면 기존 머신에는 반영되지 않는다. 배열도 통째로 기존 값이 이겨, 이미 `UserPromptSubmit` hook이 있는 머신에는 저장소 hook이 추가되지 않는다. 반영하려면 대상 파일에서 그 키를 지우고 install을 다시 실행한다
- 단점: yq의 TOML 병합 때문에 TOML 설정에 주석을 두지 못하고, Windows 경로를 슬래시로 써야 한다

### 확인 방법

#10에서 실제 `settings.json`, `config.toml`, 프로파일 사본을 병합해 사용자 값, 한글 값, Orca hook이 보존되고 두 번째 실행 결과가 같음을 확인했다.

## 선택지별 장단점

### 기존 값이 이기는 병합

- 장점: 기존 값을 지우지 않으면서 새 키를 넣는다
- 단점: 기존 키의 값을 바꾸려면 수동 조치가 필요하다

### 저장소 값이 이기는 병합

- 장점: 저장소에서 바꾼 값이 모든 머신에 반영된다
- 단점: 배열이 통째로 바뀌어 다른 도구가 넣은 hook이 사라지고, 사용자가 바꾼 값도 매번 되돌아간다

### 덮어쓰기

- 장점: 머신마다 결과가 같다
- 단점: 앱과 다른 도구가 쓴 값이 모두 사라진다

### 파일이 없을 때만 복사

- 장점: 기존 파일을 건드리지 않는다
- 단점: 저장소에 새로 추가한 키가 기존 머신에 들어가지 않는다
