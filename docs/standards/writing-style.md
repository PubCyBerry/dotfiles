# 글쓰기 규칙

저장소에 남는 글은 어떤 에이전트가 써도 같은 언어와 문체로 쓴다. 한국어로 정한 배경은 [ADR 0004](../architecture/adr/0004-write-docs-and-commits-in-korean.md)에 있고, 사용자에게 하는 보고는 [보고](agent-workflow.md#보고)를 따른다.

## 언어

| 대상 | 언어 |
|---|---|
| 문서(`*.md`), 코드 주석 | 한국어 |
| 커밋 메시지, PR 제목과 본문 | 한국어. 형식은 [커밋 규칙](commit-convention.md)을 따른다 |
| 이슈 제목과 본문 | 한국어. 형식은 [이슈 규칙](issues.md)을 따른다 |
| 스크립트가 출력하는 메시지 | 영어 |
| 식별자, 명령, 경로, 설정 키, 도구 이름 | 원어 그대로 |

- 기술 용어는 정착된 번역어가 있으면 번역어를 쓰고(저장소, 병합, 배포), 없으면 원어를 쓴다(hook, statusline, skill).
- 스크립트 출력을 영어로 쓰는 것은 기존 관례다. 로그를 검색하기 쉽고, 콘솔 인코딩 설정에 따라 글자가 깨지지 않는다.

## 문체

- 에이전트가 따르는 지침은 평서형 `~한다`체로 쓴다. `docs/`의 문서, `AGENTS.md`, `ARCHITECTURE.md`, `INSTALL.md`, `SECURITY.md`, 템플릿의 안내 주석, 코드 주석이 해당한다. 지시도 `~한다`로 쓰고 `~하세요` 같은 명령형을 쓰지 않는다(예: "먼저 조사만 한다").
- 사람이 읽는 글은 `~합니다`체로 쓰고, 변경 사항과 확인 결과처럼 나열하는 내용은 개조식 목록으로 쓴다. `README.md`, 커밋 본문, PR 본문, 이슈 본문이 해당한다. 사람에게 내용을 알리는 글이기 때문이다.
  - 문장: "`outputStyle`은 병합 대상에 이미 있으므로 install로 바뀌지 않습니다."
  - 목록 항목: "관리 상태: 2026-11-13 마지막 커밋", "로그인 없이 clone 가능 확인"
- 개조식 목록 항목은 명사나 `~함`, `~음`으로 끝내고, 아래의 조사와 어미 규칙을 적용하지 않는다.
- 문장 성분, 조사, 어미를 생략하지 않는다. "경고가 붙는다"보다 "이미 작업 중인 파일에도 경고가 붙는다"처럼 맥락을 함께 쓴다.
- 관형격 조사 `의`를 겹쳐 쓰지 않는다. "사본의 문구는 작업의 상황을"보다 "사본에 적힌 문구는 작업이 진행되는 상황을"처럼 관계를 조사와 어미로 드러낸다.
- 비유 대신 일반 어휘를 쓴다. "박는다"는 "명시한다"로, "죽는다"는 "동작하지 않는다"로 쓴다.
- 강조하는 말(진짜, 정말, 매우, 핵심적인)을 쓰지 않는다. 사실과 이유를 쓴다.
- 표의 칸, 목록 항목, 제목은 명사구로 끝내도 된다. 본문 문단은 완결된 문장으로 끝낸다.

## 기호

- 가운뎃점(`·`), 같음표(`〃`), 엠대시(`—`), 엔대시(`–`)를 쓰지 않는다. 항목을 나열할 때는 쉼표나 `와`, `과`, `나`를 쓰고, 앞뒤 문장의 관계는 콜론이나 접속사로 드러낸다.
- `--`는 명령줄 옵션(`--exact`)에만 쓴다. 본문에서 대시 대신 쓰지 않는다.

## 바뀌는 정보

- 바뀔 수 있는 세부 정보(값, 개수, 상태)를 본문에 다시 쓰지 않는다. 그 정보를 소유하거나 정의하는 대상을 가리킨다. 다시 쓴 사본은 원본이 바뀌어도 그대로 남아 틀린 정보가 된다.
  - "위에 정리한 다섯 개 필드"가 아니라 "[필드](metadata.md#필드)에 정리한 필드"라고 쓴다.
  - "Windows는 `core.autocrlf=true`를 쓴다"가 아니라 "install 스크립트의 `git config` 단계가 OS별 값을 넣는다"라고 쓴다.
- 다음은 예외다.
  - 색인(`docs/index.md`, `AGENTS.md`의 표)은 대상 문서의 제목과 `description`을 옮겨 적는다.
  - ADR의 맥락과 확인 방법에 적은 값은 결정 당시의 기록이다.

## 표기

- 경로, 명령, 설정 키, 값, 식별자는 백틱으로 감싼다.
- 저장소 파일은 저장소 루트 기준 경로로 쓴다(`config/bash/bashrc`). 홈 디렉터리 아래는 `~/`로 쓰고(`~/.claude/settings.json`), Windows에만 있는 위치는 `%APPDATA%`나 `%LOCALAPPDATA%`로 시작해 쓴다.
- OS를 나열할 때는 Windows, macOS, Linux 순서로 쓴다.
- 날짜는 `YYYY-MM-DD`로 쓰고, 시각은 ISO 8601에 시간대 오프셋을 붙여 쓴다(`2026-11-03T00:19:10+09:00`).
- 목록 기호는 `-`를 쓴다. `docs/index.md`만 OKF 색인 형식에 따라 `*`를 쓴다.

## 링크

- 저장소 안의 다른 문서는 상대 경로로 링크한다(`[설치 스크립트](installer.md)`). OKF는 `/`로 시작하는 bundle 기준 경로도 허용하지만, GitHub는 `/`를 저장소 루트로 해석하므로 쓰지 않는다.
- 특정 절을 가리킬 때는 절 제목을 링크 텍스트로 쓰고 anchor로 링크한다(`[병합 대상 파일](installer.md#병합-대상-파일)`). anchor가 깨져도 링크 텍스트로 절을 찾을 수 있다.

## 한 규칙은 한 곳에

- 같은 규칙을 두 문서에 쓰지 않는다. 한 문서에 쓰고 다른 문서에서는 링크한다. 사본이 생기면 한쪽만 고쳐지고, 에이전트는 먼저 읽은 쪽을 따른다.
- 규칙 문서(`type: Standard`)는 규칙마다 이유를 쓴다. 이유가 있어야 규칙이 다루지 않는 상황에서도 같은 방향으로 판단한다. 이유가 길면 ADR로 옮기고 링크한다.

## 문서 구조

- 본문은 front matter의 `title`과 같은 H1 하나로 시작하고, 절은 H2로 나눈다. front matter 규칙은 [문서 메타데이터](metadata.md)에 있다.
- H1 바로 아래에 문서가 다루는 범위를 한두 문장으로 쓴다.
- 규칙 문서는 함께 바뀌어야 하는 파일이 있으면 "함께 고칠 곳" 절에 표로 쓰고, 마지막 절 "검사"에 규칙을 어디서 확인하는지 쓴다(CI, 실제 실행, 리뷰).

## 코드 주석

- 코드가 보여 주지 못하는 이유만 쓴다. 코드가 하는 일을 다시 설명하지 않는다.
- 우회 코드에는 증상과 원인을 함께 쓴다. `config/bash/bashrc`의 WinGet 우회 주석이 예시다.

## 검사

자동 검사는 없다. 리뷰에서 확인한다.
